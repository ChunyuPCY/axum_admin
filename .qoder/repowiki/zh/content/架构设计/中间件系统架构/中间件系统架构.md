## 核心组件
- 上下文注入中间件（Ctx）：解析原始 URI、方法、查询参数与请求体，构建 ReqCtx 并注入到请求扩展；同时从 JWT 提取器注入 UserInfoCtx。
- 认证中间件（ApiAuth）：基于 ReqCtx 与 UserInfoCtx 判断是否为超级用户或需要校验 API 权限；若未通过则返回未授权状态码。
- 缓存中间件（Cache/SkyTableCache）：根据 API 配置决定是否启用缓存；GET 请求命中缓存直接返回，未命中则透传请求并在成功响应后异步写入缓存；变更请求触发相关缓存清理。
- 操作日志中间件（OperLog）：在请求完成后统计耗时、读取响应内容，按配置选择落库或落文件或两者；支持并发异步写入。

## 架构总览
中间件以“洋葱模型”串联，执行顺序从外到内依次为：操作日志 → 缓存 → 认证 → 上下文注入 → JWT 提取器 → 具体处理器。不同模块可按配置选择是否启用缓存与操作日志。

```mermaid
Jwt-->>Ctx : "响应"

Auth-->>Cache : "响应"

OperLog-->>Router : "响应"
Router-->>Client : "HTTP 响应"
```

## 详细组件分析

### 上下文注入中间件（Ctx）
职责
- 解析原始 URI、方法、查询参数
- 读取并编码请求体为字符串，避免后续提取器无法读取
- 构造 ReqCtx 并注入扩展
- 保持请求体可再次被下游提取器消费

执行流程

```mermaid
flowchart TD
Start(["进入 Ctx 中间件"]) --> GetURI["获取原始 URI 或使用当前 URI"]
GetURI --> BuildPath["去除前缀生成 path"]
BuildPath --> GetMethod["读取请求方法"]
GetMethod --> GetParams["读取查询参数"]
GetParams --> ReadBody["收集并读取请求体"]
ReadBody --> BuildReqCtx["构造 ReqCtx 结构体"]
BuildReqCtx --> Inject["将 ReqCtx 注入扩展"]
Inject --> NextRun["调用 next.run()"]
NextRun --> End(["返回响应"])
```

### 认证中间件（ApiAuth）
职责
- 从扩展中读取 ReqCtx 与 UserInfoCtx
- 若为超级用户则放行
- 若 API 在路由表中且需要鉴权，则校验用户对路径与方法的权限
- 未通过则返回未授权状态码

执行流程

```mermaid
flowchart TD
Start(["进入 ApiAuth 中间件"]) --> ReadCtx["读取 ReqCtx 与 UserInfoCtx"]
ReadCtx --> SuperUser{"是否超级用户？"}
SuperUser --> |是| Pass["放行 next.run()"]
SuperUser --> |否| CheckRoute["检查 API 是否在路由表中"]
CheckRoute --> |否| Pass
CheckRoute --> |是| CheckPerm["校验用户权限"]
CheckPerm --> PermOk{"权限通过？"}
PermOk --> |是| Pass
PermOk --> |否| Unauthorized["返回 401 未授权"]
Pass --> End(["返回响应"])
Unauthorized --> End
```

### 缓存中间件（Cache）
职责
- 依据 API 配置决定是否启用缓存
- GET 请求优先查缓存，命中则直接返回；未命中则透传请求并在成功时异步写入
- 非 GET 请求在成功后异步清理相关缓存键

执行流程

```mermaid
flowchart TD
Start(["进入 Cache 中间件"]) --> LoadCfg["读取 API 配置与用户信息"]
LoadCfg --> IsGet{"是否 GET 方法？"}
IsGet --> |否| NonGet["非 GET 请求：透传并清理相关缓存"]
IsGet --> |是| BuildKey["根据配置生成 data_key"]
BuildKey --> TryCache["尝试从缓存读取"]
TryCache --> Hit{"命中？"}
Hit --> |是| ReturnCache["返回缓存响应"]
Hit --> |否| Fetch["透传请求获取响应"]
Fetch --> Ok{"状态码是否 OK？"}
Ok --> |否| ReturnResp["返回下游响应"]
Ok --> |是| Save["异步写入缓存"]
Save --> ReturnResp
NonGet --> ReturnResp
ReturnCache --> End(["结束"])
ReturnResp --> End
```

## 性能考量
- 中间件顺序
  - 操作日志与缓存均会引入额外 IO，建议仅在需要时启用；GET 请求的缓存命中可显著降低延迟
- 缓存策略
  - 内存缓存适合低延迟场景；SkyTable 缓存适合分布式部署与持久化需求
  - 变更请求的异步清理可减少一致性风险，但需注意清理粒度与性能开销
- 日志
  - 文件与数据库写入均为异步，避免阻塞主链路；可根据流量调整日志级别
- 请求体读取
  - Ctx 中间件会完整读取请求体并重建，避免下游提取器失效；大体积请求体可能增加内存占用

## 故障排查指南
- 401 未授权
  - 检查 JWT 是否有效、是否在线；确认认证中间件是否正确注入 ReqCtx 与 UserInfoCtx
  - 确认 API 是否在路由表中且需要鉴权
- 缓存未生效
  - 检查 API 配置中的 data_cache_method 与 log_method
  - 确认请求方法是否为 GET；变更请求是否正确清理相关缓存键
- 操作日志缺失
  - 检查配置项是否启用操作日志；确认 API 配置的日志策略
  - 观察异步写入是否报错（日志中会记录失败信息）
- 请求体为空
  - 确认 Ctx 中间件已正确读取并重建请求体；避免下游重复消费

## 结论
Axum Admin 的中间件体系采用清晰的洋葱模型，围绕上下文、认证、缓存与日志四大能力构建。通过配置驱动的中间件装配，可在不同模块灵活启用/禁用特定能力。实践中建议：
- 严格控制中间件顺序，确保上下文与认证前置
- 按模块精细化启用缓存与日志
- 关注大请求体与高并发下的内存与 IO 压力
- 通过异步写入与过期清理保障性能与一致性

### 配置项与特性开关
- 中间件特性
  - cache-mem：启用内存缓存中间件
  - cache-skytable：启用 SkyTable 缓存中间件
- 路由配置
  - cache_time：缓存时间（秒），为 0 表示禁用缓存
  - cache_method：缓存方式（0=内存，其他=SkyTable）
  - enable_oper_log：是否启用操作日志
  - api_prefix：API 前缀，用于路径标准化
